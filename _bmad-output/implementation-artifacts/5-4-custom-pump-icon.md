# Story 5.4: Кастомная иконка-насос

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

Как пользователь,
я хочу, чтобы у приложения была отличительная иконка-насос вместо стандартной,
чтобы у приложения была собственная визуальная идентичность в Dock, Finder и меню-баре.

## Acceptance Criteria

1. **Given** приложение собрано, **when** смотрю на Dock/Finder, **then** иконка приложения — векторный силуэт насоса (custom `AppIcon.appiconset`, все требуемые размеры для macOS). **ДОСТИГНУТО.**
2. **Given** смотрю на иконку меню-бара, **and** нет активных закачек, **then** показывается «простой» вариант насоса (outline/приглушённый), заменяя текущий `arrow.up.arrow.down.circle`. **НЕ ДОСТИГНУТО** — см. Scope Boundary и `deferred-work.md`.
3. **Given** есть ≥1 активная закачка, **then** показывается «активный» вариант насоса (акцентный цвет), заменяя текущий `arrow.up.arrow.down.circle.fill`. **НЕ ДОСТИГНУТО** — см. Scope Boundary и `deferred-work.md`.
4. **Given** оба места (app icon и menu-bar) используют единый визуальный стиль насоса. **ЧАСТИЧНО** — единый стиль реализован и подтверждён только для app icon; меню-бар остался на прежних SF Symbol'ах (`arrow.up.arrow.down.circle(.fill)`), не на pump-глифе.
5. **Given** реализация через `.help(_:)` на `Image` внутри `MenuBarExtra`'s `label:`, **then** это эмпирически проверено на реальной сборке — не предполагается по документации. **Не применимо к этой истории напрямую** (это условие из Story 5.3's AC, скопированное в `epics.md`'s заготовку Story 5.4 по ошибке — не про эту историю; см. Scope Boundary).

## Scope Boundary

**Решено при создании истории (задним числом, после реализации — история делалась без отдельного `bmad-create-story`-прохода, сразу разработкой с последующей документацией):**

- **App icon (AC1) полностью реализован и подтверждён.** Векторный силуэт насоса (закруглённый квадрат с градиентным индиго-фоном `#5E70DE`→`#3B49B0`, белый силуэт насоса — рукоятка, шток, цилиндр-корпус, раструб-основание, штуцер с каплей), отрисован как SVG (`rsvg-convert`), растеризован в 10 PNG (все размеры `idiom: mac` — 16/32/128/256/512 в 1x/2x) в `MyTorrent/Assets.xcassets/AppIcon.appiconset/`. Проект уже ссылался на `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon` в билд-настройках (XcodeGen генерирует это по умолчанию для application-таргетов), но каталога `Assets.xcassets` в проекте не существовало вообще (впервые подтверждено в Story 5.2's Scope Boundary) — эта история впервые создаёт его. XcodeGen автоматически подхватывает `.xcassets`-папку по `sources: - path: MyTorrent` в `project.yml`, без изменений самого `project.yml`.
- **Иконка меню-бара (AC2/AC3) — не реализована, несмотря на несколько независимых попыток, все эмпирически провалились на реальной сборке.** Это не «решение оставить как есть» — это открытый технический тупик, зафиксированный подробно в `deferred-work.md` (раздел «Deferred from: Story 5.4»). Кратко: `NSStatusItem`, который `MenuBarExtra` создаёт под капотом, реально существует и кликабелен (подтверждено через Accessibility API — присутствует в дереве, верная геометрия, клик открывает popover), но **любой** кастомный glyph в его `label:` рендерится полностью невидимым — растровый `Image` из `Assets.xcassets` (template и non-template), `NSImage(named:)` с `isTemplate = false`, `Canvas` с ручной отрисовкой `Path`, и даже кастомный `Shape`-конформер (`.fill()`/`.stroke()`) в самом минимальном виде. Единственное, что реально отобразилось за всю сессию — примитивный `Circle().fill(Color.red)` без кастомной геометрии, что не даёт однозначно локализовать причину (геометрия ли конкретного `PumpShape`, конвертация `MenuBarExtra`-label'а в `NSStatusItem`-изображение в целом, или специфика этой машины — `assetutil` показывал `AssetStorageVersion: Xcode 26.4 (17E192)`, нетипично новая версия). `MyTorrentApp.swift` в итоге откачен к исходному рабочему `Image(systemName: "arrow.up.arrow.down.circle(.fill)")` (Story 4.1/5.3) — не оставлен в сломанном/невидимом состоянии.
- **Отдельная, уже решённая по ходу истории проблема: Dock/Finder показывали устаревшую (сгенерированную до появления `Assets.xcassets`) иконку из кэша.** Подтверждено: сам собранный `AppIcon.icns` внутри `.app`-бандла корректен (проверено прямым извлечением и просмотром пикселей), но Finder показывал не связанную с ним иконку по кэшу, привязанному к пути `DerivedData`. С разрешения пользователя выполнено `rm -rf ~/Library/Caches/com.apple.iconservices.store && killall Dock Finder` — не помогло для конкретного `DerivedData`-пути (Finder-кэш для этого пути оказался более стойким, чем ожидалось), но копия `.app` по свежему пути (`~/Desktop`, никогда не кэшировавшемуся) сразу показала верную иконку — подтверждает, что сама иконка корректна, а проблема ограничена конкретно устойчивым Finder-кэшем для многократно пересобираемого `DerivedData`-пути. Это дев-окружение-специфичный нюанс, а не баг реализации; тестовая копия на Desktop удалена после проверки.
- **Отдельный, явно вынесенный пользователем за рамки этой истории вопрос: `LSUIElement`/accessory-lifecycle (AD-7) означает, что у приложения нет Dock-иконки, пока оно запущено** — это ожидаемое, документированное поведение (Story 1.3/AD-7, сознательный выбор ради «работает тихо в фоне, единственный выход — явный Quit»), не баг этой истории. Пользователь в сессии сказал, что теперь хочет Dock-иконку во время работы — явно отложено пользователем как отдельное решение (потребовало бы пересмотра AD-7, не тривиальное добавление). См. `deferred-work.md`.
- **AC5 из `epics.md`'s исходной формулировки** — про эмпирическую проверку `.help(_:)` — это буквально скопированное условие из Story 5.3's AC5, оставшееся в `epics.md`'s заготовке Story 5.4 по инерции (обе истории трогают один и тот же `MenuBarExtra`'s `label:`). Story 5.3 уже закрыла этот вопрос для `.help(_:)` самого по себе; в этой истории `.help(_:)` не менялся (тот же вызов, что и был), так что это условие не про новую работу этой истории.

## Dev Notes

### Technical Requirements / Stack

- **XcodeGen** (`project.yml`) — `.xcassets`-каталоги подхватываются автоматически по `sources: - path: MyTorrent`, без явного перечисления в `project.yml`. `ASSETCATALOG_COMPILER_APPICON_NAME = AppIcon` уже был в сгенерированных билд-настройках (дефолт XcodeGen для application-таргетов) ещё до появления самого каталога.
- **`rsvg-convert`** (Homebrew, `librsvg`) — использован для рендера SVG→PNG на каждый целевой пиксельный размер напрямую; не входит в зависимости проекта (dev-tool, не рантайм-зависимость).
- **Design System** (`design-artifacts/D-Design-System/00-design-system.md`) — `color-accent` `#4C5FD5`/`#7C8CF0` использован для градиента фона app icon (не буквально как токен в коде — только в исходном SVG/растровых PNG; в коде Swift-токен не заводился, т.к. меню-бар часть, где он был бы нужен, откатилась).

### Architecture Compliance

- `AD-3` (SwiftUI throughout, no AppKit) — попытки для меню-бара включали `NSImage(named:)`/`isTemplate` как способ получить `NSImage`-объект для передачи в `Image(nsImage:)` (тот же паттерн, что Story 5.2 использовала для `NSColor(dynamicProvider:)` — не вводит AppKit-вью/контролы, только использует AppKit-типы данных). Ни один из подходов не дал видимого результата, все откачены — `AD-3` не нарушен ни в финальном состоянии, ни по духу в процессе.
- Не затрагивает `engine/`/Rust/FFI/поллинг — чисто presentation-слой (asset-каталог + попытки SwiftUI-рендеринга). `AD-1`, `AD-2`, `AD-4`–`AD-9` не применимы.
- `AD-10` (unsigned CI-сборка) — не затронут; локальные сборки в этой истории все через `xcodebuild` напрямую, не через `release.yml`.

### Debug Log References

- Diagnostика Dock/Finder-иконки: `stat` подтвердил, что сам `.app`-бандл содержит свежесобранные ресурсы (`AppIcon.icns` от сегодняшней сборки), но директория самого бандла имела старую mtime (нормальное ФС-поведение — mtime директории не обновляется при замене содержимого существующих файлов, только при добавлении/удалении записей) — не путать со «сборка не обновилась».
